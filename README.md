# Shopping Cart System

Take-home assignment — full stack engineer position, אגף התקשוב ומערכות המידע, משרד הביטחון.

Three independently deployable services: `server-catalog` (.NET 10 + EF Core + SQL Server, screen 1), `server-orders` (NestJS + Elasticsearch, screen 2), `client` (React + Redux Toolkit + Vite + TypeScript, both screens). `docker-compose.yml` and `.env` live at the repo root and can bring up all three, plus both datastores — see *Running everything in Docker* below.

Each service has its own README with setup, tests and design notes — see [Services](#services) below. Everything in this repo is cross-platform (Windows / macOS / Linux); no OS-specific tooling anywhere.

## Running everything in Docker (optional)

Neither backend API nor `client` is containerized by default — the setup steps below run `dotnet run`/`npm run start:dev`/`npm run dev` directly against just `catalog-sql`/`orders-es` in Docker, which is faster to iterate against than rebuilding a container image on every change. `server-catalog/Dockerfile`, `server-orders/Dockerfile`, and `client/Dockerfile` (all multi-stage: SDK/Node build stage, slim ASP.NET Core/Node/nginx runtime stage) exist for the case where you want to check the whole thing runs the way it'd actually deploy — one instance each, not three long-lived local processes:

```
docker compose --profile full up -d --build
```

`catalog-api`/`orders-api`/`client` in `docker-compose.yml` are gated behind the `full` [profile](https://docs.docker.com/compose/how-tos/profiles/) specifically so a plain `docker compose up -d` (see *Running it without Docker* below) is completely unaffected by their existing — it still starts only `catalog-sql`/`orders-es`, same as before these were added. `catalog-api` waits on `catalog-sql`'s health check the same way `dotnet run` waits on it manually today (see *Design notes*); `orders-api` waits on `orders-es`'s the same way `OrdersRepository.onModuleInit`'s retry-ping does; `client` just waits on the other two to start (no health check to wait on — nginx serving static files has nothing to become ready, and the app already has its own loading/error state for a not-yet-up API, see `CatalogPage.tsx`). `client`'s two `VITE_*` values are baked into its JS bundle at build time (Vite doesn't read them at runtime) as build args in `docker-compose.yml`, pointing at `catalog-api`/`orders-api`'s host-published ports — the browser calls those directly, not through the `client` container's own network.

## server-catalog — Catalog API

Read-only categories/products catalog. Layered: `Catalog.Domain` (entities) → `Catalog.Application` (DTOs, service interfaces) → `Catalog.Infrastructure` (EF Core, repository) → `Catalog.Api` (controllers, HTTP entry point). Each of those three layers registers its own services (`AddApplicationServices()`, `AddInfrastructureServices()`); a fifth, dedicated project — `Catalog.DependencyInjection`, sitting right beside the other four under `src/` — owns the actual composition (`CompositionRoot`), so `Program.cs` reduces to one call and the whole DI story is a project you can see in the tree, not a detail buried in the entry point. See `architecture.md` in the project notes for the full rationale and diagrams.

**A note on scope.** I added a fair amount beyond what a read-only, two-endpoint catalog for a take-home strictly needs — cursor pagination, a rate limiter and a global concurrency limiter, API versioning, a dedicated logging module, `IMemoryCache`, and a `/health` endpoint. None of it is required to satisfy the assignment as stated; I added it because a short interview process doesn't leave much room to show how I actually reason about a system meant to run past a demo — under load, under partial failure, over time — and this seemed like the honest way to show that instead of just asserting it. Every addition is explained in *Design notes / trade-offs* below, including where I judged something further (a distributed cache, a message queue, full observability) to be genuinely disproportionate for this scope and left it out on purpose — see *Possible improvements* below, and the root README's system-wide *Possible improvements* section for the cross-cutting pieces (auth, Redis, a message queue, a reverse proxy) that apply to both services at once.

### 1. Configure local secrets (never committed) — from the repo root

```
cp .env.example .env
```

Open `.env` and set your own `MSSQL_SA_PASSWORD` (needs an uppercase letter, a lowercase letter, a digit and a symbol — SQL Server enforces this). `.env` is gitignored; `docker-compose.yml` reads it automatically because they're in the same folder. `.env.example` is the only one checked into git, so anyone cloning the repo knows exactly which variables to set.

### 2. Start SQL Server — from the repo root

```
docker compose up -d
```

Brings up `catalog-sql` with a health check, so anything that depends on it later knows to wait until it's actually ready to accept connections, not just "container started." (Apple Silicon: this image only ships for `linux/amd64` and runs under emulation — works, just slower to start; see the comment in `docker-compose.yml`.)

### 3. Point the API at it — from `server-catalog/`

```
node scripts/setup-local-secrets.mjs
```

One script (not a `.ps1`/`.sh` pair to keep in sync — Node already runs on every platform and is a project-wide dependency regardless). It reads the password straight out of the repo-root `.env` (so it's typed in exactly one place, never copy-pasted a second time) and writes it into `dotnet user-secrets` — a JSON file in your user profile, *outside* the repo entirely. Never ends up in git, never ends up in `appsettings.Development.json`. `Catalog.Api.csproj` already declares a `UserSecretsId`, so this is wired up out of the box. Verify without printing the password: `dotnet user-secrets list --project src/Catalog.Api`.

### 4. Restore — from `server-catalog/`

```
dotnet restore src/Catalog.Api/Catalog.Api.csproj
```

### 5. Product images — already in the repo, nothing to run here

`src/Catalog.Api/wwwroot/images/` already ships the product photos the demo catalog references — committed to the repo (15 of 18; see *Design notes* below for the other 3), so a normal `git clone` already has them and the app has zero runtime dependency on any external image host from the start.

`scripts/download-product-images.mjs` is the script that originally fetched them (from each product's `imageUrl` in `catalog-demo-data.json`, into this same folder, printing a per-file report — size + content type, flagged if suspiciously small). It was a one-time step, not part of a normal setup — kept in the repo for reference and for the one case it'd actually be needed again: `wwwroot/images/` missing files you expect to see (a clone that dropped them somehow, or you deleted the folder locally):

```
node scripts/download-product-images.mjs
```

Skip this step entirely on a normal checkout.

### 6. Create the initial migration — from `server-catalog/`

```
dotnet ef migrations add InitialCreate --project src/Catalog.Infrastructure --startup-project src/Catalog.Api -o Persistence/Migrations
```

Migration files aren't checked in yet — generate them once locally, then commit the generated `Persistence/Migrations` folder for the actual submission.

### 7. Run — from `server-catalog/`

```
dotnet run --project src/Catalog.Api/Catalog.Api.csproj
```

The schema is created and three demo categories with 18 products are seeded automatically on first run (idempotent — safe to restart; already have a populated database from an earlier run and want the new products? `docker compose down -v` from the repo root wipes the SQL volume, then repeat steps 2–7).

Swagger UI opens at **http://localhost:5080/swagger**. Try `GET /api/v1/categories`, `GET /api/v1/categories/{categoryId}/products?limit=5` for a cursor-paginated page of one category's products, or `GET /health` for the liveness/readiness check.

### Tests

```
cd server-catalog
dotnet test
```

> `server-catalog/global.json` pins `"test": { "runner": "Microsoft.Testing.Platform" }`. Without it, `dotnet test` on the .NET 10 SDK fails with *"Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later"* — the SDK dropped the old VSTest bridge for xunit.v3 projects (they use Microsoft.Testing.Platform natively), and .NET 10 needs this opt-in at the solution level rather than a per-project MSBuild property. One file, next to `Catalog.slnx`, fixes `dotnet test` for all three test projects at once. See [dotnet/sdk#51283](https://github.com/dotnet/sdk/issues/51283).

`tests/Catalog.Application.Tests` covers `CategoryService` — the one place with actual logic in this service (mapping domain entities to DTOs, keeping products correctly nested under their own category) — and its own DI registration. `tests/Catalog.Infrastructure.Tests` covers: the swappable-repository DI wiring (both the SQL Server and in-memory paths resolve, each now wrapped in the `CachingCategoryRepository` decorator); `InMemoryCategoryRepository`'s data integrity and its cursor-pagination logic (a bounded first page with a non-null cursor when more remain, and walking the cursor to the end returns every product in the category exactly once); and `CachingCategoryRepository` itself, against a real `IMemoryCache` rather than a mock of one — that a second call to the full-catalog read is actually served from cache instead of hitting the inner repository again, and that the paginated read deliberately is not cached (it hits the inner repository every time). `tests/Catalog.DependencyInjection.Tests` covers `CompositionRoot` itself — that it rejects null dependencies in its constructor, and that its `RegisterCatalogServices()` wrapper actually resolves both layers end to end through one entry point, not just that each layer's own extension method works in isolation. Not covered on purpose: `CategoryRepository` (a thin `Include`/`Where`/`OrderBy`/`Take` + `ToListAsync`, no custom logic — testing it would mostly be testing EF Core itself) and the controller (thin pass-throughs). Chasing 100% coverage on a read-only service this small would be padding, not signal — the tests exist to protect the mapping and caching/pagination logic, not to hit a number.

**Manually verifying the rate limiter.** The sliding-window limiter (`PermitLimit: 100` per 60s, per client — see `appsettings.json`'s `RateLimiting` section and *Design notes* below) isn't exercised by the automated tests above — it's a cross-cutting HTTP concern, not application logic, so it's easier to just hit the running API directly and watch it kick in. With `server-catalog` running (`dotnet run`, default `http://localhost:5080`), from PowerShell:

```powershell
1..150 | ForEach-Object {
    try { (Invoke-WebRequest -Uri "http://localhost:5080/api/v1/categories" -UseBasicParsing).StatusCode }
    catch { $_.Exception.Response.StatusCode.value__ }
}
```

Expect a run of `200`s followed by `429`s once the 100-request limit for the current window is used up — the exact cutover point can land a little before or after 100 depending on timing across the limiter's 4 segments (`SegmentsPerWindow`), not necessarily exactly on request 101. A `429` response body is the same `ErrorEnvelopeDto` JSON every other error path returns (see *Design notes*), not an empty response. This only exercises the per-client sliding-window limiter — the requests above run one at a time, so nothing here hits the separate global concurrency limiter, which only rejects when multiple requests are genuinely in flight at once.

### Design notes / trade-offs

- **.NET 10** is the version this assignment's stack calls for — not just whatever happened to be newest when this was written. It's also the current LTS release (support runs into ~2028), so "the version the assignment specifies" and "the actively maintained version" happen to be the same thing here, not a trade-off between them.
- **Cross-platform by construction**: one Node-based setup script instead of a `.ps1`/`.sh` pair (Node is already required for the other two services, so this adds no new dependency and avoids maintaining two scripts that could drift out of sync); `docker-compose.yml` pins `platform: linux/amd64` on the SQL Server image since Microsoft doesn't publish an arm64 build, so Apple Silicon still works (under emulation) instead of failing to find a matching image.
- **Secrets**: local dev password lives in a gitignored `.env` at the repo root (read by docker-compose) and in `dotnet user-secrets` (for the API, outside the repo entirely) — never in a file that gets committed. `.env.example` documents the required variables with a placeholder value so a reviewer knows exactly what to set. A full secrets vault (HashiCorp Vault, Azure Key Vault, etc.) would be disproportionate here: this is a single-reviewer take-home meant to be cloned and run once, and standing up vault infrastructure would work *against* the assignment's explicit ask for clear, simple install instructions, not for it. `.env` + `.env.example` + user-secrets is the standard, right-sized pattern for exactly this situation.
- **Dependency injection is a first-class, browsable thing here, not an implementation detail**. Two levels of this: (1) each layer keeps its *own* registration in a `DependencyInjection/` folder (`Catalog.Application/DependencyInjection/`, `Catalog.Infrastructure/DependencyInjection/`) rather than a loose file — visible in the tree, not just in `Program.cs`. (2) Composing those layers together is its *own project* — `src/Catalog.DependencyInjection/`, a sibling of `Catalog.Api`, `Catalog.Application`, `Catalog.Domain` and `Catalog.Infrastructure` right under `src/`, impossible to miss when browsing the repo. It holds `CompositionRoot`, an explicit **Composition Root** (Mark Seemann's term): a class whose *constructor* takes the `IServiceCollection` and `IConfiguration` composition actually needs (with null-guards), and whose `RegisterCatalogServices()` *wrapper method* calls both `AddApplicationServices()` and `AddInfrastructureServices()` behind one name — so `Catalog.Api` is reduced to `new CompositionRoot(builder.Services, builder.Configuration).RegisterCatalogServices();` and doesn't need to know which layers exist or in what order they must be wired. Giving a two-call wrapper its own assembly is more ceremony than strict YAGNI would allow at this size — a deliberate, documented exception, made because the goal here is demonstrability: making "composition happens in exactly one obvious place" a fact about the file tree, not just a claim in this README. More importantly, `ICategoryRepository` has **two** real implementations — `CategoryRepository` (EF Core/SQL Server) and `InMemoryCategoryRepository` (zero dependencies) — switchable with one config flag (`Catalog:UseInMemoryStore`, or env var `Catalog__UseInMemoryStore=true`) with no changes anywhere in `Catalog.Application` or `Catalog.Api`, because both only ever depend on the interface. `Catalog.Infrastructure.Tests/DependencyInjectionTests` proves both paths actually resolve through the container in isolation, and `Catalog.DependencyInjection.Tests/DependencyInjectionTests` proves the same thing through `CompositionRoot` itself, end to end. Handy side effect: `dotnet run` with that flag set runs the whole API with no Docker/SQL Server at all — useful once the client exists and needs a catalog to talk to quickly.
- **`Product` carries two image fields on purpose: `ImageUrl` (external source) and `ImagePath` (local, served) — not one field doing both jobs.** `ImageUrl` is the original link a photo was found at (Wikimedia Commons, Pixabay, Tnuva, a Google Images cache thumbnail, ...); `scripts/download-product-images.mjs` fetches each one once into `src/Catalog.Api/wwwroot/images/`, and `ImagePath` is the resulting same-origin path (`/images/apples.jpg`) that `Catalog.Api` actually serves via `app.UseStaticFiles()`. Keeping both means neither piece of information is lost: `ImageUrl` documents where the photo came from (useful for swapping it out or checking the source later), while the app itself never has a runtime dependency on Tnuva/Google/Wikimedia staying reachable — a broken third-party host can't break a page load, because the file the client actually requests already lives in this repo. Not every source is equally durable — a couple of `ImageUrl` values are Google Images cache thumbnails, small and not meant for long-term linking — which is exactly why `ImagePath` exists as the thing that's actually depended on.
- **15 of 18 products carry a photo; the remaining 3 (Chicken Drumsticks, Ground Beef, Turkey Breast) have both `ImageUrl` and `ImagePath` null on purpose.** The client is designed to fall back to a local placeholder image whenever `ImagePath`/`ImageUrl` are empty or fail to load (`architecture.md`, ADR #9), so a `null` seed value exercises that fallback path deliberately rather than being unfinished work — add a real photo for those three the same way (pick a source URL, download it, drop the file in `wwwroot/images/`, add one line to the script and to `CatalogDemoData`) whenever one's picked out.
- **Catalog data lives in `catalog-demo-data.json`, not hardcoded as C# object initializers.** `CatalogDemoData.BuildCategories()` deserializes it (embedded resource, so no file-path/copy-to-output issues across projects) and maps it onto the domain entities in a loop — adding a product is a one-line JSON edit, not a new C# statement.
- **`CatalogSeeder` and `InMemoryCategoryRepository` share one data source, `CatalogDemoData`.** Both `ICategoryRepository` implementations used to hand-duplicate the same product list — and it had already drifted: after the catalog grew from 9 to 18 products, `InMemoryCategoryRepository` still had the original 9. `CatalogDemoData.BuildCategories()` is now the single place product/category data (names, Hebrew names, `ImageUrl`, `ImagePath`, `UnitPrice`, `Unit`) lives; `CatalogSeeder` inserts it into SQL Server, which assigns real `Id`s via the identity column, and `InMemoryCategoryRepository` assigns its own sequential, category-coded `Id`s (`101`, `102`, ... for category `1`) afterward, since it has no database to do that for it. Same content, two backends, no copy-paste drift possible.
- **`Product` now carries `UnitPrice` (`decimal(10,2)`) and `Unit` (a three-member `ProductUnit` enum — `Kilogram`/`Piece`/`Liter` — stored as its member name via `.HasConversion<string>()`, not the underlying int, for the same "readable straight out of a SQL query" reason `ImagePath`/`ImageUrl` already get a plain `nvarchar` rather than something more exotic).** `decimal(10,2)` for `UnitPrice` for the same reason it's used everywhere else money shows up in this project: exact two-decimal-place ILS, not the binary floating point `double`/`float` would give. `ProductDto`/`Program.cs` register a `JsonStringEnumConverter` (`AddControllers().AddJsonOptions(...)`) so the HTTP response actually serializes `"unit": "Kilogram"` as a string — the same converter `CatalogDemoData` already needed to deserialize `catalog-demo-data.json`'s `"unit": "Kilogram"` values in the first place, now applied on the way out too, so a client reading a raw response never has to look up what a bare `1` means. `client/src/api/types.ts` mirrors this with a plain `'Kilogram' | 'Piece' | 'Liter'` union type — the natural client-side equivalent of a string-serialized C# enum, not a second numeric enum with its own mapping table to keep in sync.
- **One caveat worth being upfront about: the migration for this (`AddProductPriceAndUnit`) was hand-written, not generated by `dotnet ef migrations add`** — this environment has no `dotnet` tooling available to actually run it. I mirrored the exact structure `dotnet ef` produces for the existing `InitialCreate` migration as closely as I could by hand (same `Up`/`Down` shape, same `Designer.cs` snapshot format, `CatalogDbContextModelSnapshot.cs` updated identically — diffing the two Designer-style files shows only the expected differences: the `using`/`[Migration(...)]`/class-declaration lines every migration's own Designer.cs carries that a snapshot doesn't), but I haven't been able to run `dotnet build` or apply it to confirm it's actually correct. Treat it as unverified until you run it yourself — `CatalogSeeder.SeedAsync` already calls `dbContext.Database.MigrateAsync()` unconditionally before its "already seeded, skip" check, so on a fresh clone `dotnet run` applies it automatically, no separate `dotnet ef database update` step needed. One thing worth knowing if you're updating an *already-seeded* database from before this change rather than starting fresh: the migration back-fills existing rows with `UnitPrice = 0` / `Unit = "Kilogram"` defaults, not the real values from `catalog-demo-data.json` — a schema migration can't retroactively know each product's actual price, and `CatalogSeeder` only inserts seed data into an empty `Categories` table. To pick up the real per-product prices on an existing database, wipe and reseed the same way step 7 already describes for any other seed-data change: `docker compose down -v` from the repo root, then repeat steps 2–7.
- **Cursor (keyset) pagination on `GET /api/v1/categories/{categoryId}/products`, not offset/skip.** `ICategoryRepository.GetProductsPageAsync` orders by `Id` and filters `Id > cursor`, so each page costs the same whether it's page 1 or page 10,000 — an offset-based `Skip(n).Take(m)` gets slower (and, under concurrent inserts, can skip or repeat rows) the deeper you page. The main `GET /api/v1/categories` endpoint stays unpaginated on purpose: at 18 products it's one cheap payload, and pagination only earns its complexity once a catalog is large enough that "return everything" stops being the cheaper option — which is exactly the products-within-a-category endpoint's job here.
- **The paginated endpoint's response now carries a `meta: { limit, total }` object alongside `items`/`nextCursor` — deliberately no `page` number.** `limit` is the page size actually applied (after clamping in the controller), `total` is the full product count for the category across every page (`CategoryRepository`/`InMemoryCategoryRepository` both count it independently of the cursor filter). No `page`, for the same reason `server-orders`' equivalent `meta` omits one (see its README): keyset pagination has no offset to divide by a page size — a client can only walk forward one `nextCursor` at a time, so a page number would be a value that looks meaningful without actually being one.
- **`IMemoryCache`, wired in as a decorator (`CachingCategoryRepository`), not scattered `if (cache.TryGetValue(...))` calls inside the repository itself.** It wraps whichever concrete repository `Catalog:UseInMemoryStore` selects and implements the same `ICategoryRepository` interface, so nothing above it (the service, the controller) can tell it's there. Only `GetAllWithProductsAsync` is cached (TTL from `Caching:CategoriesTtlSeconds`, default 60s) — the paginated query is deliberately left uncached, since its result depends on `(categoryId, cursor, limit)` and caching every combination would defeat the point of paging a large catalog. `CachingCategoryRepositoryTests` verifies both halves of that claim against a real `IMemoryCache`, not a mock of one.
- **Rate limiting and a global concurrency limiter, both from ASP.NET Core's built-in `System.Threading.RateLimiting` — no extra NuGet package.** A per-client (by IP) sliding-window limiter protects against one caller hammering the API; a separate *global* concurrency limiter caps how many requests are in flight at once across every client, which is what actually protects the SQL Server connection pool from being exhausted by a burst — the sliding window alone wouldn't, since it counts per client, not requests in flight. Both are configured through `RateLimitingOptions`, bound from a `RateLimiting` config section with defaults baked into the C# properties themselves (sliding window: 100 requests/60s; concurrency: 50 in flight), following the exact same pattern as `Catalog:UseInMemoryStore` — override with `RateLimiting__PermitLimit=200`, etc., or leave it alone and get sane defaults. (The root `.env` file is read by `docker-compose.yml` for the SQL Server container only — the API itself isn't containerized *by default* (see *Running everything in Docker*), so its own config comes from `appsettings.json`, environment variables, or `dotnet user-secrets`, the same channels `Catalog:UseInMemoryStore` already uses; the optional `catalog-api` container reads the same environment-variable channel, just set in `docker-compose.yml` instead of a shell.) `/health` is explicitly exempted (`.DisableRateLimiting()`) so a monitoring probe can never itself get rate-limited or count against the concurrency budget meant for real traffic.
- **API versioning via a plain `api/v1/[controller]` route prefix — no `Asp.Versioning.Mvc` package.** The simplest thing that actually works for a single-consumer API: if the shape ever needs to change in a breaking way, `v2` sits beside `v1` rather than breaking the existing client.
- **Logging is its own DI module (`Catalog.Api/Logging/LoggingExtensions.AddCatalogLogging`)**, not a handful of calls sitting inline in `Program.cs`. It swaps the default console formatter for ASP.NET Core's built-in structured JSON console formatter — no external framework (Serilog, NLog) needed for output that's already machine-parseable. Paired with `RequestLoggingMiddleware`, the outermost middleware in the pipeline (registered before even `ExceptionHandlingMiddleware`, so it wraps everything): it assigns or forwards an `X-Correlation-Id` for every request, echoes it back in the response header, and logs one structured line per request (method, path, status, elapsed ms) — enough to trace a single request end to end in the logs, or to tie a bug report from a client back to the exact server-side log line.
- **`AddCatalogLogging` has two output modes, not one — the same fix already made for server-orders' `JsonLogger`, for the same reason.** The first version always emitted flat JSON lines. Correct for a log-aggregation pipeline, but genuinely worse to read than ASP.NET Core's own default console output when actually staring at a terminal — raised directly after seeing it. Rather than picking one at the expense of the other, `ASPNETCORE_ENVIRONMENT=Production` now gets the structured JSON console formatter; anything else (Development — what `dotnet run`/`launchSettings.json` set locally — and Staging) gets ASP.NET Core's built-in simple console formatter: short, single-line, human-read text instead of a JSON object per entry. This needs no extra configuration to do the right thing in either place: `dotnet run` locally already sets `Development` via `launchSettings.json`, and a real deployment (the Dockerfile, or any host that doesn't override it) defaults to `Production` on its own when the variable is unset — mirroring exactly how `NODE_ENV=production` drives the same decision on the NestJS side.
- **EF Core's per-command SQL logging (`Microsoft.EntityFrameworkCore.Database.Command`, e.g. `[20101]`/`CommandExecuted` in the logs) is now filtered to `Warning` in `appsettings.json`, next to the existing `"Microsoft.AspNetCore": "Warning"` line.** That numeric `[EventId]` after the category name isn't specific to this project or to EF Core — it's how .NET's console formatter labels every log entry (`Category[EventId]`), so the message type can be filtered or matched on a stable ID instead of parsing wording; it isn't something the simple-console formatter can be told to hide. What actually made the output noisy was EF Core logging the full SQL text and parameter values for every single database round trip at `Information` level, which the app's `"Default": "Information"` log level picked up by default since nothing narrowed it. Silencing that specific category down to `Warning` — the same treatment already given to `Microsoft.AspNetCore`'s own framework noise — removes it from both the readable dev console and the JSON production stream; genuine EF Core warnings/errors (e.g. a failed migration) still come through.
- **`/health` is a real ASP.NET Core health check (`Microsoft.Extensions.Diagnostics.HealthChecks`), not a hand-rolled `200 OK` action.** It only checks the database when the API is actually backed by one (`DatabaseHealthCheck.CanConnectAsync()`, skipped entirely under `Catalog:UseInMemoryStore`) — a hand-written `IHealthCheck` rather than the separate `...HealthChecks.EntityFrameworkCore` NuGet package, since `IHealthCheck` itself already ships in the ASP.NET Core shared framework and one `CanConnectAsync()` call didn't justify a new dependency.
- **`/health` didn't show up in Swagger at all until this was fixed — `app.MapHealthChecks(...)` alone doesn't document itself.** `MapHealthChecks()` returns `IEndpointConventionBuilder`, and `.Produces<T>()` (the standard way to document a minimal-API response for Swashbuckle's `AddEndpointsApiExplorer()`) is only defined for the more specific `RouteHandlerBuilder` that `MapGet`/`MapPost`/etc. return — `IEndpointConventionBuilder` doesn't support it ([dotnet/aspnetcore#43985](https://github.com/dotnet/aspnetcore/issues/43985), still open). Rather than pull in a third-party package (`Swashbuckle.AspNetCore.HealthChecks` exists for exactly this) or hand-construct `IProducesResponseTypeMetadata` objects, `/health` is now mapped with a plain `app.MapGet("/health", ...)` that calls `HealthCheckService.CheckHealthAsync()` itself — the same call `MapHealthChecks` makes internally — and returns a typed `HealthCheckResponseDto`, which `.Produces<HealthCheckResponseDto>(200)`/`.Produces<HealthCheckResponseDto>(503)` can document normally. Side effect, not the goal: the response body is now real JSON (`{ status, totalDurationMs, checks: { database: { status, description, durationMs } } }`) instead of the bare `"Healthy"`/`"Unhealthy"` text `MapHealthChecks` writes by default — matches `report.Status` mapping to 200/503 the same way `MapHealthChecks`' own default `ResultStatusCodes` does (`Degraded` still counts as 200, only `Unhealthy` is 503).
- **Read-only endpoint, no input validation** — the only write path in this service is the startup seeder, so there's no command-validation layer to build.
- **`NameEn` + `NameHe` as two plain columns**, not a translations table — there are exactly two languages and that isn't expected to grow; a generic i18n schema would be over-engineering for this scope.
- **Migrations auto-apply at startup** — convenient for a single-instance local/demo setup. A real multi-instance deployment would run migrations as a separate release step instead.
- **No HTTPS redirection locally** — the dev launch profile is plain HTTP by design; a containerized deployment would terminate TLS at a reverse proxy instead.
- **Unhandled exceptions** are caught by `ExceptionHandlingMiddleware` and returned in the shared error envelope (`{ status, message, errors[] }`) that `server-orders` will also use, so the client has one error handler for both backends. That envelope is now a real documented type, `ErrorEnvelopeDto` (`[JsonPropertyName]` keeps the wire format lowercase despite PascalCase C# properties) — not just an anonymous object serialized inline — used by both `ExceptionHandlingMiddleware` *and* the rate limiter's `OnRejected` handler (see below), so there's exactly one shape to document and one for a client to handle, not one ad hoc shape per failure path.
- **Every endpoint's possible response codes are now documented in Swagger, not just the happy path.** `[ProducesResponseType(typeof(ErrorEnvelopeDto), 429)]`/`[ProducesResponseType(typeof(ErrorEnvelopeDto), 500)]` sit once at the controller level on `CategoriesController` (both are possible on every action in it — 429 from either rate limiter, 500 from `ExceptionHandlingMiddleware`, which wraps every request regardless of which action ran), rather than repeated on each action. The rate limiter previously set only a status code on rejection (`RejectionStatusCode = 429`) with no response body at all — `OnRejected` now writes the same `ErrorEnvelopeDto` JSON every other error path uses, so the 429 Swagger now documents is what a caller actually receives, not a guess. One honest asymmetry worth naming: unlike `server-orders`, where the throttler (429) and the concurrency middleware (503) are genuinely different status codes, .NET's rate limiter middleware shares one `RejectionStatusCode`/`OnRejected` pair across *both* the sliding-window and the global concurrency limiter — a rejection here is always 429, whichever limiter caused it, and there's no way for the client to tell which from the response alone. Not fixed, because it isn't broken: both failure modes mean the same thing to a caller ("retry later"), and giving them different codes would mean tracking which limiter fired just to pick a number.
- **`server-catalog`/`server-orders` each got a multi-stage `Dockerfile`** (SDK/Node build stage → slim ASP.NET Core/Node runtime stage) — see *Running everything in Docker* at the top of this README for how to actually run them. Neither is part of the default `docker compose up -d` (gated behind Compose's `full` profile) — the setup steps below still run each API directly (`dotnet run`/`npm run start:dev`) against just the two database containers, since that stays faster to iterate against than rebuilding an image on every change.

### Possible improvements

Scoped out for a take-home assignment — framed as what I'd add next to take this from a demo to something production-ready, not just gaps left unspoken.

- **Replace the static JSON seed with a real content-management path.** `catalog-demo-data.json` is fine for 18 demo products reviewed once, but a real catalog needs an admin UI or a product-management API, so adding a product doesn't require a code change and a redeploy.
- **Paginate `GET /api/v1/categories` too, and add filtering/full-text search by name.** Cursor pagination already covers products within a category (`GET /api/v1/categories/{categoryId}/products` — see *Design notes*); the top-level listing would get the same treatment once the catalog has enough categories for it to matter — at 3 categories today it would be pure overhead.
- **Move product images to blob storage (Azure Blob/S3) behind a CDN, with the API only storing the reference.** Local files under `wwwroot/images/` are fine for one instance, but don't survive horizontal scaling — a second replica wouldn't have the files a request landed on the first one expects.
- **Add distributed tracing and metrics (OpenTelemetry), not just structured logs.** `RequestLoggingMiddleware` plus the JSON console formatter give one correlatable log line per request, enough to debug a single instance by hand — not enough to follow one request across multiple services or graph latency/error-rate over time.

## server-orders — Orders API

Order creation and cursor-paginated order history, backed by Elasticsearch instead of a relational database. Layered: `src/orders/dto` (request/response shapes) → `src/orders/repositories/orders.repository.ts` (the only file that talks to Elasticsearch) → `src/orders/orders.service.ts` (mapping, cursor encode/decode, page-size clamping) → `src/orders/orders.controller.ts` (HTTP entry point). `src/common/` holds the cross-cutting pieces — logging, the error filter, health. See `architecture.md` in the project notes for the full rationale.

**A note on scope.** I added a fair amount beyond what a create-and-list orders API for a take-home strictly needs — cursor pagination, rate limiting, API versioning, a dedicated logging module, a real health check, and a unified error envelope. None of it is required to satisfy the assignment as stated; it's here to show how I actually reason about a system meant to run past a demo, not just to assert that I can. Every addition is explained in *Design notes / trade-offs* below, including a couple of things I deliberately left out because they didn't fit this platform's own concurrency model — see that section for why, and *Possible improvements* for what's honestly still missing.

### Tests

```

```

`cursor.util.spec.ts` covers the pagination cursor as a pure, framework-free function pair: encode/decode round-trips a `[createdAt, _id]` sort-value tuple unchanged, the encoded form is URL-safe (no raw `"` or `/`), and a malformed or wrong-shaped cursor throws rather than silently producing garbage. `orders.service.spec.ts` covers `OrdersService` against a mocked `OrdersRepository`: `createOrder` delegates and maps the result correctly; `getOrdersPage` defaults the page size to 20 when none is given, clamps it to 100 when a caller asks for more, encodes the repository's raw sort values into the opaque `nextCursor` string returned to the client, returns `meta.limit`/`meta.total` from what the repository reports, and rejects a malformed cursor with a 400 *before* it ever reaches Elasticsearch (not by catching whatever error Elasticsearch happens to throw for a bad `search_after` value). Not covered *here* on purpose: `OrdersRepository` itself — it's a thin wrapper over a client SDK (index creation, `index()`, `search()` with `search_after`) with no branching logic of its own; a mocked unit test of it would just be asserting that a mock returns what you told it to. That's what the e2e suite below is for instead.

```
cd server-orders
npm run test:e2e
```

`test/orders.e2e-spec.ts` boots the *real* `AppModule` — real `ElasticsearchModule`, real `OrdersRepository`, a real Elasticsearch client — and drives it over actual HTTP with `supertest`, the same global prefix/versioning/`ValidationPipe` wiring `main.ts` applies for a real run. It's the deliberate complement to the mocked unit suite above, not a duplicate of it: `orders.service.spec.ts` verifies `OrdersService`'s own logic in isolation (defaulting, clamping, cursor encoding); this suite verifies the whole stack wired together the way `docker compose up -d && npm run start` actually runs it — creating an order and getting it back out through real pagination, the shared `{ status, message, errors[] }` envelope on a validation failure (missing field, invalid email, empty `items`, an unknown top-level field rejected by `forbidNonWhitelisted`), a malformed cursor rejected with 400 before it reaches Elasticsearch, and `GET /health` reporting Elasticsearch as genuinely up. **Needs a real, reachable Elasticsearch** at `ELASTICSEARCH_NODE` (`docker compose up -d` from the repo root, same prerequisite as *Run* above) — there's no mocking here, on purpose, since the entire point is exercising `OrdersRepository` against the real thing. No cleanup between runs, either: there's no `DELETE` endpoint (out of scope for this assignment, same as the rest of the surface), so every run leaves its orders in the index — fine for a demo index you don't mind never staying clean, not something to point at data you care about.

I could not run this suite myself in either of my execution environments — no Docker/Elasticsearch reachable from the cloud container I work in, and `docker` itself isn't installed in the device-bridge shell on your machine either — so it still needs a real run on your end to confirm. What I *could* verify from here: `tsc --noEmit` against a dedicated `tsconfig.e2e.json` (see *Design notes* below) is clean except for the one expected error — `Cannot find module 'supertest'`, since `npm install` hasn't run yet to pick up the new `supertest`/`@types/supertest` devDependencies — and running `jest --config ./test/jest-e2e.json` directly confirms it fails at exactly that one point and nowhere else, i.e. the test-runner wiring itself (config, `rootDir` override, module resolution) is sound; only the missing package and the missing live Elasticsearch stand between this and a real green run.

### Design notes / trade-offs

- **`search_after` keyset pagination, not offset/`from`+`size`.** Elasticsearch has no single auto-increment id to filter on, so the cursor is a composite `[createdAt, id]` sort-value tuple instead of one number, encoded as an opaque `base64url(JSON(...))` string (`cursor.util.ts`) so the client never needs to know its shape. Page 10,000 costs the same as page 1 this way — offset/`from`+`size` gets slower the deeper you page, and Elasticsearch itself deprecates it past 10,000 results for exactly that reason.
- **The tiebreaker field is a plain `id` keyword field on the document, not Elasticsearch's own `_id`.** The very first version sorted on `_id` directly — since the document's `_id` already *is* the order's id (see `create()` below), it looked redundant to store it twice. It isn't: sorting on `_id` fails outright with `illegal_argument_exception` / "Fielddata access on the `_id` field is disallowed" — Elasticsearch doesn't build doc values for `_id` by default, specifically to discourage sorting on it. `search_after` still needs a genuinely unique tiebreaker alongside `createdAt` (two orders can share a timestamp), so the same UUID used as the document `_id` is *also* stored as an ordinary `id: keyword` field in `INDEX_MAPPING`, and that's what `findPage()` actually sorts and pages on. Found by actually paginating past the first request, not by reading the mapping back.
- **`GET /api/v1/orders` returns a `meta: { limit, total }` object alongside `items`/`nextCursor` — deliberately no `page` number.** `limit` is the page size actually applied (after defaulting to 20 or clamping to 100), and `total` is the full count of orders matching the query across every page, sourced from Elasticsearch via `track_total_hits: true` in `findPage()` (without it, ES stops counting past its default 10,000-hit cap, so `total` would silently go wrong on a large index). A `page` number doesn't have a coherent meaning here on purpose: `search_after`/cursor pagination has no offset to divide by a page size — a client can't jump to "page 7" the way it could with `Skip(n).Take(m)`, only walk forward one `nextCursor` at a time — so reporting one anyway would just be a number that looks meaningful and isn't.
- **`@nestjs/throttler` for rate limiting — fixed-window-per-TTL, not sliding window, worth saying plainly rather than mislabeling it.** It's a per-client request count that resets every `RATE_LIMIT_TTL_SECONDS`, not a continuously sliding one. It still protects against the same class of abuse — one client hammering the API — just with coarser boundary behavior at the edge of each window. Configured through `RateLimitModule.forRootAsync`, reading `RATE_LIMIT_TTL_SECONDS`/`RATE_LIMIT_LIMIT` from config. `/health` is exempted via `@SkipThrottle()`, so a monitoring probe can never itself get rate-limited.
- **A hand-written `ConcurrencyLimitMiddleware`, scoped to `OrdersController`'s routes only.** This was deliberately left out of the first version of this service: a concurrency limiter mainly earns its keep protecting a thread pool or database connection pool from being exhausted by a burst of concurrent requests, and Node's single-threaded event loop plus the Elasticsearch client's own internal connection pooling and request queuing already handle that differently. On reflection that reasoning covers *why the platform doesn't need one to stay correct* — it doesn't cover the separate concern of bounding how much work this one process takes on at once, which matters regardless of platform: a slow downstream Elasticsearch query, or a burst of legitimate traffic from many different clients, can still pile up more in-flight work than this process should try to hold simultaneously, and rate limiting (`@nestjs/throttler`, above) doesn't help here either, since it limits how often *one client* can call an endpoint, not how many requests *in total* are being processed right now. The middleware keeps a single shared in-flight counter (a singleton provider, registered in `AppModule`'s `providers`, so Nest's DI resolves it once for the whole process rather than per request) and rejects new requests with a `503` once `MAX_CONCURRENT_REQUESTS` (default 50) is already in flight, releasing the count on the response's `finish`/`close` events. Scoped to `OrdersController` only, not every route, so `GET /health` stays responsive to a monitoring probe even while orders traffic is saturated.
- **`server-orders` also got a multi-stage `Dockerfile`** (Node build stage, installs everything and runs `npm run build`, → slim runtime stage, production dependencies only plus the compiled `dist/`) — see *Running everything in Docker* in the root README for how to actually run it. Not part of the default `docker compose up -d` (gated behind Compose's `full` profile) — `npm run start:dev` against just `orders-es` in Docker stays the faster loop for actual iteration.
- **Nest's built-in URI versioning (`VersioningType.URI`, `defaultVersion: '1'`)** — zero extra packages, `api/v1/[controller]`-shaped routes. `HealthController` opts out of it explicitly (`@Controller({ path: 'health', version: VERSION_NEUTRAL })`) — `enableVersioning()` applies the version prefix to every controller by default, independent of the global `api`-prefix exclusion in `main.ts` (which only strips `api`, not the version segment). Missed this the first time: the app ran and `/health` *looked* right in the code, but the real running server actually answered on `/v1/health`, not `/health` as documented — caught only by hitting the live endpoint, not by reading the source back. Fixed with `VERSION_NEUTRAL`.
- **Request bodies are capped at `BODY_SIZE_LIMIT` (default `1mb`), applied explicitly rather than left to whatever express happens to default to.** `NestFactory.create` is called with `bodyParser: false` and `main.ts` wires the `json`/`urlencoded` parsers back up itself via `app.useBodyParser(...)`, each given the configured limit — turning the body-size cap from an accident of the underlying HTTP library's own defaults into a real, documented, overridable setting (`.env.example`).
- **A hand-written `JsonLogger implements LoggerService`, not Winston or Pino.** Nest's `LoggerService` interface is five methods, and doesn't need a logging framework behind it. (Subclassing `ConsoleLogger` was considered and rejected — its internal formatting hooks aren't stable public API to override against.) Paired with `RequestLoggingMiddleware`, applied to every route in `app.module.ts`'s `configure()`: it assigns or forwards an `X-Correlation-Id`, echoes it back in the response header, and logs one structured line per request (method, path, status, elapsed ms).
- **`JsonLogger` has two output modes, not one.** The first version always emitted flat JSON lines — correct for a log-aggregation pipeline (ELK/Datadog/CloudWatch, or `jq`), but genuinely worse to read than Nest's own default console output when actually staring at a terminal during `npm run start:dev` — raised directly after trying it. Rather than picking one at the expense of the other, `NODE_ENV=production` now switches to the flat JSON format; anything else (including unset, the default for local dev) gets a colored, single-line human-readable format closer to Nest's own. A structured object message (`RequestLoggingMiddleware`'s `{ correlationId, method, path, statusCode, elapsedMs }`) is rendered as `key=value` pairs in human mode and as flat top-level JSON fields in production mode — never double-encoded into a nested string either way. This needs no extra configuration to do the right thing in either place: a real deployment (containers, PM2, most hosting platforms) already sets `NODE_ENV=production` on its own.
- **`AllExceptionsFilter` was logging the sanitized client-facing message for unexpected 500s, not the real exception's own message.** `envelope.message` is always the generic `"An unexpected error occurred."` string for anything that isn't an `HttpException` — correct to send to the client (never leak internals), wrong to *also* log server-side instead of the actual error, which left the terminal saying only that something broke, not what. Fixed: the log line now carries the real exception's `message` (the client response is unaffected, still the generic envelope).
- **Two rough edges found by actually clicking through Swagger, not by reading the code back — both fixed.** `JsonLogger` originally `JSON.stringify`'d a non-string `message` into a nested, double-escaped string instead of merging its fields into the log entry, so `RequestLoggingMiddleware`'s structured request logs came out unreadable (`"message":"{\"correlationId\":...}"` instead of flat `correlationId`/`method`/`path` fields) — fixed by spreading an object message directly into the entry. Separately, `GET /api/v1/orders`'s `cursor`/`limit` query parameters showed up in Swagger UI as *required strings*, even though the controller method already declares them optional: `@nestjs/swagger` can't infer optionality or the intended number type from a bare `@Query()` parameter, so it defaulted to marking both required and typed as `string` — fixed with explicit `@ApiQuery({ required: false, type: ... })` on each.
- **`/health` uses `@nestjs/terminus`'s modern `HealthIndicatorService` API** (not the older `HealthIndicator` base class) for a hand-written `ElasticsearchHealthIndicator` — one `client.ping()` call. `@nestjs/terminus` already ships the health-check aggregation machinery (`HealthCheckService`, the `@HealthCheck()` decorator, the response shape), so only the one Elasticsearch-specific check needed writing.
- **Unified error envelope (`{ status, message, errors[] }`) via a global `AllExceptionsFilter implements ExceptionFilter`** — deliberately the same shape as `server-catalog`'s `ExceptionHandlingMiddleware`, per `architecture.md`'s cross-service contract, so the client needs exactly one error handler for both backends. `class-validator`'s array-of-strings validation errors are special-cased into the `errors` array rather than left as one flattened `message` string.
- **That envelope is now a documented `ErrorEnvelopeDto` class, not just the `ErrorEnvelope` TypeScript interface `AllExceptionsFilter` types itself against internally.** `@nestjs/swagger` can't generate a schema from a bare interface — it has no runtime representation once TypeScript compiles it away, only `@ApiProperty()`-decorated classes carry the metadata Swagger needs. `OrdersController` now documents every response code each route can actually return, not just the happy path: `@ApiResponse({ status: 429, type: ErrorEnvelopeDto })`/`@ApiResponse({ status: 503, type: ErrorEnvelopeDto })` sit once at the controller level (both are possible on every route — 429 from the global `ThrottlerGuard`, 503 from `ConcurrencyLimitMiddleware`, which is scoped to this whole controller), plus `400` on each route individually (validation failure on `POST`, malformed cursor on `GET`) since those differ per route rather than applying uniformly.
- **One shared `ElasticsearchModule` providing a single `Client` instance** (via an `ELASTICSEARCH_CLIENT` provider token), imported by both `OrdersModule` and `HealthModule` — one connection pool for the whole app, not one per module that happens to need the client.
- **The orders index is created automatically on startup** (`OrdersRepository.onModuleInit`, checking `indices.exists` before `indices.create`) — convenient for a single-instance local/demo setup, not how a real multi-instance deployment would sequence a schema change. `onModuleInit` also waits for Elasticsearch to actually be reachable first (`client.ping()`, up to 20 attempts / 3s apart) before trying to create anything — found the hard way, when starting `server-orders` immediately after `docker compose up -d` crashed the app outright with a raw `ConnectionError`, because the compose command returns as soon as the container *starts*, not once Elasticsearch is actually ready to accept connections (which can take anywhere from a few seconds to over a minute locally). `docker-compose.yml`'s own healthcheck on `orders-es` (see *Design notes* point 11 in `architecture.md`) stops *other containers* from starting against a not-yet-ready Elasticsearch, but nothing enforced the same ordering for `server-orders` running locally (`npm run start:dev`, outside Docker) — this retry loop is that missing piece, logged through `JsonLogger` so a slow-starting Elasticsearch shows up as a few `warn` lines instead of a crash. The optional containerized `orders-api` (see *Running everything in Docker*) doesn't strictly need the retry loop, since its `depends_on: condition: service_healthy` already sequences it after `orders-es` is ready — the retry loop stays in either way, since it costs nothing when Elasticsearch is already up and is what actually protects the local, non-Docker run.
- **Orders are indexed with `refresh: 'wait_for'`**, so a `POST` is immediately visible to the very next `GET` — important for a demo where "create an order, then see it in the history list" needs to work without a race. The trade-off, honestly: `wait_for` adds latency to every write and doesn't scale the same way under real indexing throughput, where Elasticsearch's default near-real-time (roughly one-second-delayed) refresh interval is the right choice. See *Possible improvements*.
- **`typescript` is pinned to `^5.7.3`, not the newest available major.** TypeScript reached 7.0 shortly before this was written (the new native Go compiler, "tsgo"), and it was tempting to just grab the newest tag. Checked first, though: `ts-jest`'s own `peerDependencies` caps at `>=4.3 <6`, and TS 7 breaks it (and current ESLint) outright as of this writing. "Current" and "newest tag" aren't always the same thing — 5.7.3 is the current version of the toolchain that actually works together; 7.0 would have shipped a project that doesn't build its own tests.
- **The whole `@nestjs/*` stack is pinned to `^11.2.3`, one minor behind the `12.0.1` that `npm install` would pick by default — caught by an actual failed install, not by research alone.** The first version of this `package.json` pinned everything to `^12.0.x`, since that genuinely was the newest tag for every package involved. Running `npm install` against it surfaced a real `ERESOLVE` conflict: `@nestjs/terminus` at the time only declared support for `@nestjs/common`/`@nestjs/core` `^10.0.0 || ^11.0.0`. Re-checking the registry turned up a second, quieter one `npm` hadn't even reported yet — `@nestjs/throttler` has not published anything past `6.5.0`, and that version's own `peerDependencies` caps at `^11.0.0` too. `@nestjs/core` v12 releases very recently, and the two rate-limiting/health packages this project depends on simply hadn't caught up to it yet. Rather than forcing the mismatch through with `--legacy-peer-deps` (masking a real incompatibility instead of fixing it) or dropping a package, every `@nestjs/*` package was pinned to `11.2.3` — the last 11.x release before 12.0.0 — which every dependency here (including `@nestjs/config` and `@nestjs/swagger`, whose own peer ranges explicitly cover both 11 and 12) declares real support for. Same principle as the TypeScript pin directly above it: "current" means "the newest combination that installs and runs together," not "whatever `npm view <pkg> version` prints for each package in isolation." A second, different-shaped problem showed up one step later, after `npm install` succeeded: `npm test` failed with `SyntaxError: Unexpected token 'export'` inside `@nestjs/config`'s own compiled output. That's not a peer-dependency mismatch (`^12.0.0`'s peer range genuinely does allow `@nestjs/common ^11.0.0`, which is why npm was happy to install it) — it's that `@nestjs/config@12.0.0` ships ESM-only output (`export * from './conditional.module.js'`, no CommonJS build), part of Nest 12's "ESM-ready packages" push, and this project's `ts-jest`/CommonJS toolchain can't `require()` that. Rather than reconfiguring Jest for ESM just to accommodate one dependency, `@nestjs/config` is pinned to `^4.0.4` — the last release before the ESM jump, still on the same `@nestjs/common ^10.0.0 || ^11.0.0` peer range this project already needs, and a plain CommonJS build. Same lesson twice over: a clean `npm install` only proves the versions *resolve*, not that they actually run together.
- **`CreateOrderDto` uses `fullName`, not separate `firstName`/`lastName` fields** — the assignment specifies three input fields (name, address, items), so splitting name into two doesn't reflect anything the spec actually asked for.
- **`npm run build` silently produced no `dist/` at all — no error, exit code 0 — a real, documented Nest CLI bug, not a config mistake in this project.** [nestjs/nest-cli#3312](https://github.com/nestjs/nest-cli/issues/3312): Nest CLI's compiler wrapper prefers TypeScript's `createIncrementalProgram` when available, and under a specific combination — `incremental: true` in `tsconfig.json`, `deleteOutDir: true` in `nest-cli.json` (both present here, both individually reasonable), plus a stale `.tsbuildinfo` from an earlier build — that API reports `emitSkipped: false` while actually writing zero files. Fixed with the workaround the issue documents: `tsconfig.build.json` (what `npm run build` actually compiles with) now overrides `incremental: false`, so the one-shot production build never takes the broken incremental path — `tsconfig.json` itself keeps `incremental: true`, since that's still a genuine editor/watch-mode performance win for `npm run start:dev`, which was never affected by this bug in the first place. The stale `.tsbuildinfo` that triggered it also had to be deleted once by hand.
- **`tsconfig.json` has four small, deliberate corrections over the Nest CLI's default scaffold, all found by the editor's own TypeScript diagnostics, not by `tsc` failing outright.** `baseUrl` is removed entirely rather than kept — nothing in this codebase imports through a bare-specifier alias (every import is relative, e.g. `../../elasticsearch/...`), it was dead config inherited from the default scaffold, and TypeScript is deprecating it ahead of removal in TS7 anyway, so there was nothing worth keeping it for. `rootDir: "./src"` is now explicit, matching the Jest config's own `rootDir: "src"`, instead of leaving TypeScript to infer the emitted `dist/` layout from whichever files happen to get compiled. `strictPropertyInitialization: false` is now explicit rather than left to TypeScript's implicit default — the DTO classes throughout this project (`CreateOrderDto`, `OrderItemDto`, ...) are plain `class-validator`/`class-transformer`-decorated property bags populated at runtime from the request body, not constructor-initialized, which is the standard, correct pattern for Nest DTOs — but relying on an *unset* option to quietly default to `false` is exactly the kind of implicit behavior that a newer TypeScript version's changed defaults can silently break; making it explicit removes that risk entirely, regardless of which TypeScript version actually compiles this project. `"types": ["node", "jest"]` is now explicit too, fixing an editor-only `Cannot find name 'describe'` (TS2593) error in the `.spec.ts` files — TypeScript normally auto-includes every `@types/*` package found in `node_modules` when `types` is left unset, which is why `npm test` itself never failed, but naming the two packages this project actually relies on removes any dependency on that implicit auto-discovery behaving the same way across editors/TS versions.
- **`Unsupported route path: "/api/*"` (`LegacyRouteConverter`) is a known, cosmetic, framework-internal warning — not a bug in this code, and left as-is on purpose.** It comes from `app.setGlobalPrefix('api', { exclude: [...] })`'s own internal route-pattern generation colliding with a newer `path-to-regexp` version Nest 11 pulls in; Nest auto-converts the pattern and continues correctly (confirmed: `/health`, `POST`/`GET /api/v1/orders` all resolve and respond as expected). It fires once at application startup, not per request. NestJS's own maintainers closed the equivalent upstream report as "not planned" ([nestjs/nest#14513](https://github.com/nestjs/nest/issues/14513)) — there's no supported workaround to chase, so it's documented here instead of "fixed" with a workaround that would just be papering over an acknowledged framework quirk.
- **`test/orders.e2e-spec.ts` needed its own `tsconfig.e2e.json`, not just a `test/jest-e2e.json` copied from Nest's default scaffold.** `tsconfig.json`'s `rootDir: "./src"` is deliberate (see the `tsconfig.json` bullet above) and correct for everything that lives in `src/` — but a file under `test/`, outside that `rootDir`, trips TypeScript's `TS6059` ("File is not under 'rootDir'") the moment `ts-jest` tries to compile it against the same `tsconfig.json` the unit tests already use without issue (they're all inside `src/`, so they never hit this). Rather than loosening `rootDir` on the tsconfig the *production build* (`tsconfig.build.json`) and every other tool still relies on, `tsconfig.e2e.json` extends `tsconfig.json` and overrides just `rootDir` to `"."` — scoped to `ts-jest`'s e2e run alone, wired in via `test/jest-e2e.json`'s `transform` option (`["ts-jest", { "tsconfig": "tsconfig.e2e.json" }]`). `tsconfig.build.json` additionally excludes `test` outright, alongside its existing `*.spec.ts`/`*.mock.ts` exclusions — `nest build` has no reason to ever try compiling e2e tests into `dist/`.

### Possible improvements

Scoped out for a take-home assignment — framed as what I'd add next to take this from a demo to something production-ready, not just gaps left unspoken.

- **Add filtering/search to `GET /api/v1/orders`** — by customer, date range, or status. Cursor pagination covers walking the full history efficiently; it doesn't cover finding one order, which a real orders API would need (Elasticsearch is a natural fit for that once it's needed — this just isn't built yet).
- **Run Elasticsearch as a real multi-node cluster, with replica shards and TLS/auth in front of it**, instead of the single `discovery.type: single-node` instance with security disabled used for this demo.
- **Drop `refresh: 'wait_for'` in favor of Elasticsearch's default refresh interval, or a separate read model, once write throughput matters.** It's the right call for a demo's immediate read-after-write expectation, but won't scale under real write load — a production system would design the client around eventual consistency instead.
- **Add distributed tracing and metrics (OpenTelemetry), not just structured logs.** `RequestLoggingMiddleware` plus `X-Correlation-Id` covers tracing one request by hand through the logs, not graphing latency/error-rate over time or visualizing a trace across service boundaries.
- **Wire the e2e suite (`npm run test:e2e`, see *Tests* above) into a CI pipeline with a disposable Elasticsearch test container**, instead of it only ever running against whatever Elasticsearch happens to be up on a developer's machine. The suite itself already exercises `OrdersRepository` against a real Elasticsearch — the gap left is making that automatic rather than something a person has to remember to have running locally before `npm test` — see *Add a CI pipeline* in the root README's system-wide *Possible improvements*.

## client — Shopping Cart UI

**A note on scope.** This is the two screens the assignment actually asks for (shopping list, order summary) plus a few things beyond the literal wireframe: i18n (en/he) with RTL/LTR, MUI as the component library, and a per-product-card quantity stepper instead of a single category-dropdown → product-dropdown → quantity-field → "add" flow — the stepper *is* the "add to cart" action, so the same requirement (pick a category, pick a product in it, set a quantity, add it) is satisfied with fewer clicks once every product for the selected category is already on screen.

### How the two screens work

#### Screen one — shopping list (`/`)

One request on page load, `GET /api/v1/categories`, brings back every category with its products already nested — no follow-up round trip once the page has loaded. Tabs across the top filter which categories are shown; picking one filters from data already in the store, not a second request. Each product is a card with its own quantity stepper (`−` / count / `+`) instead of a separate dropdown-and-"add"-button flow — clicking `+` both picks that product and adds a unit to the cart at once, and clicking it again on a product already in the cart tops up its quantity instead of creating a duplicate line; clicking `−` steps it back down, removing the line entirely once it reaches 0. A bar sticky to the bottom of the screen shows the total item count and a "Continue to order" button, disabled until the cart has at least one item in it.

#### Screen two — order summary (`/checkout`)

The cart is shown read-only first, then the three required fields (full name, email, address). Validation runs on submit — client-side (`checkoutValidation.ts`) and, independently, server-side too once the request actually reaches `server-orders` (`CreateOrderDto` enforces the same three checks with `class-validator`, regardless of what the client already caught). "Confirm order" posts to the Orders API; on success the screen shows the confirmation with the new order's id and empties the cart. Landing on `/checkout` with nothing in the cart (a refresh, or the URL typed directly) doesn't silently redirect — it shows an explicit empty-cart message with a button back to the catalog instead, since a silent redirect could read as the page failing to load rather than telling you why there's nothing to check out.

### Design notes / trade-offs

* **MUI as the component library, with `@mui/stylis-plugin-rtl` for RTL.** Uses an Emotion cache with the RTL stylis plugin swapped in dynamically based on the active language (`ThemeDirectionProvider.tsx`). We use the official MUI-scoped package (`@mui/stylis-plugin-rtl`) for long-term maintenance compatibility.
* **React Router with two routes (`/`, `/checkout`).** Provides proper browser history, native back-button support, and distinct URLs for each screen without manual state management for view switching.
* **The quantity stepper on each product card acts as the "add to cart" action.** By displaying all products per category simultaneously, clicking `+` immediately initializes and increments the item in the cart, compressing the traditional multi-step flow into a single, intuitive interaction.
* **Normalized Redux cart state (`cartSlice`).** State is structured by `productId` (`{ items: { [productId]: { ... } } }`), mirroring the exact payload shape expected by `POST /api/v1/orders` for seamless request mapping.
* **RTK Query for API integration (`catalogApi`, `ordersApi`).** Leverages two distinct `createApi` instances configured with respective `VITE_CATALOG_API_URL` and `VITE_ORDERS_API_URL` environment variables.
* **Lightweight i18n via `i18next`/`react-i18next`.** Language persistence relies on `localStorage` with `navigator.language` as a fallback, avoiding heavy localization detector dependencies.
* **Robust product image fallback chain.** Implements `imagePath`/`imageUrl`/local-placeholder resolution paired with native browser lazy loading (`loading="lazy"`).
* **Type-safe unit mapping.** Uses a shared `ProductUnit` union type (`'Kilogram' | 'Piece' | 'Liter'`) mapped directly to localized translation keys (`catalog.unit.*`), ensuring UI units remain consistent with backend enums.
* **Multi-stage Docker support.** Includes a `Dockerfile` utilizing a Node build stage transitioning to a lightweight `nginx:alpine` runtime serving static assets, complete with SPA fallback routing rules.
* **Order summary shows unit price, a per-line total, and a grand total.** Cart lines snapshot `unitPrice`/`unit` from the product at the moment they're added (`cartSlice.ts`), not re-read live from the catalog — so `/checkout` reflects the price the shopper actually saw. Each line reuses the same `catalog.pricePerUnit` translation key `ProductCard` already shows; a new `selectCartTotalPrice` selector sums `unitPrice × quantity` across every line for the grand total. Display-only — `POST /api/v1/orders` still sends just `productId`/`productName`/`categoryName`/`quantity`, since `server-orders` doesn't store prices at all.
* **Cart persists across a page reload (`localStorage`), same mechanism as the language preference.** `cartSlice.ts` reads the cart back from a single `shopping-cart-system.cart` key once at store-creation time and `store.ts` writes it back via `store.subscribe`, on any real change to the `cart` slice (a reference-equality check, so unrelated actions like catalog/orders fetches or checkout-form typing don't trigger a write). The read side is defensive rather than trusting stored data outright: malformed JSON, or a stored shape from an older version of the app, falls back to an empty cart; a single malformed line inside an otherwise-valid cart is dropped without discarding the rest.
